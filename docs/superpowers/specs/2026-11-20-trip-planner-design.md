# 길찾기 설계

- 작성일: 2026-11-20
- 상태: 초안 (사용자 검토 전)
- 상위 문서: [`2026-11-05-mvp-design.md`](2026-11-05-mvp-design.md)(이하 "MVP 설계")
- 함께 읽을 문서: [`2026-11-20-mvp4-map-design.md`](2026-11-20-mvp4-map-design.md)(이하 "지도 설계"). 길찾기는 지도 위에 올라갑니다.
- 근거: 2026-11-20 브레인스토밍과 조사 네 건(경로 API, 장소 검색 API, 자체 계산 가능성, TMAP). 조사 요약은 7장에 있습니다.

**[사용자 결정]**은 사용자가 직접 정한 것이고, **[설계 판단]**은 설계자가 정한 것입니다. 설계자가 제안하고 사용자가 "그렇게 해줘"로 받은 것은 사용자 결정으로 적습니다.

## 1. 왜 하는가

- 쓰는 상황은 이렇습니다. **주말에 처음 가는 곳을, 현재 위치에서 검색합니다.** [사용자 결정]
- 지금은 이런 때 네이버지도나 카카오맵을 씁니다. Betro를 열 이유는 차별점 하나입니다. **[사용자 결정]**
  - **지금 출발하면 걸어서 닿을 수 있는 차량**을 기준으로 경로를 비교합니다.
  - 보통 길찾기는 "버스 3분 뒤 도착"처럼 정류장 기준으로 알려 줍니다. 정류장까지 5분을 걸어야 하면 그 버스는 못 탑니다. Betro는 그 버스를 놓친다고 말하고, 실제로 탈 다음 차 기준으로 도착 시각을 냅니다.
- 이 계산은 출퇴근 안내에 이미 있습니다(`packages/commute/src/session/estimate.ts`의 `estimateRoute`). 길찾기는 그 계산을 등록하지 않은 경로에도 쓰는 일입니다.

## 2. 정한 것 [사용자 결정] (2026-11-20)

### 2.1 범위

- 길찾기는 이번 MVP 범위 안입니다. MVP 설계 2장 "범위 밖"의 "앱이 경로를 찾아 주는 기능" [사용자 결정]을 사용자가 뒤집었습니다.
- **서울, 경기, 인천을 처음부터 다룹니다.** 서울 목적지만 먼저 하지 않습니다.
- 길찾기 결과로 연 경로에 경기·인천 버스가 있으면 지도에 띄우고, 사용자가 그 경로를 보는 동안만 관측합니다(지도 설계 2.7).
- **길찾기는 1차 출시를 막지 않습니다.** 1차 출시는 지금 기준(출퇴근, 지도, 찾기와 상세)으로 하고, 길찾기는 준비되는 대로 업데이트로 붙입니다. 붙일 때의 기준은 두 가지입니다. 하나는 iOS와 Android 실기기에서 "검색 → 결과 → 안내 모드 → 잠금화면 → 종료" 흐름이 끝까지 통과하는 것입니다. 다른 하나는 "탈 수 있어요" 정확도를 기록하는 것인데, 이건 보고만 하고 출시를 막지 않습니다. (2026-11-20)

### 2.2 검색

- 출발지는 기본으로 현재 위치입니다. 목적지는 장소 이름이나 주소로 검색합니다.
- 들어오는 곳은 지도의 "어디로 가세요?"입니다. 장소가 없을 때 보이는 카드(지도 설계 2.5)에도 있습니다.

### 2.3 결과 화면: 처음 탈 차량이 먼저 보인다

- 결과를 열면 **처음 타야 할 대중교통의 위치**가 가장 먼저 눈에 들어와야 합니다.
- 지도는 세 가지가 한 화면에 들어오게 맞춥니다.
  - 내 위치
  - 정류장(역)까지 걷는 길(점선)과 걷는 시간
  - 그 정류장으로 다가오는 첫 차량과 "6분 뒤" 같은 도착까지 남은 시간
- 아래 카드에는 경로 후보가 **"지금 출발하면 탈 수 있는 차" 기준 도착 시각** 순으로 나옵니다. 카드마다 다음을 보여 줍니다.
  - 도착 시각
  - "탈 수 있어요", "빠듯해요", "곧 오는 차는 놓쳐요" 중 하나. 판단에는 출퇴근과 같은 여유 폭을 씁니다(정확도 우선 설계, `packages/commute/src/session/margin.ts`). 추정값 위에는 "탈 수 있어요"를 쓰지 않는다는 규칙도 같습니다. **[설계 판단]** 공식 도착 예측은 ±1분이 47~70%만 맞기 때문에, 단순 비교로는 "탈 수 있어요"가 자주 틀립니다(5장 첫 실패 기준). 그래서 시안의 두 상태에 "빠듯해요"를 더합니다.
  - 정류장에서 기다리는 시간
  - 실시간인지 시간표 추정인지
- 다른 카드를 누르면 지도의 첫 차량이 그 경로의 차량으로 바뀝니다. 못 타는 차량은 다른 색(시안에서는 빨강)으로 그립니다.
- 다음 차의 위치가 아직 없으면 그렇다고 알립니다. 시간표 추정 상태의 버스는 지도에 그리지 않습니다(MVP 설계 5.8).

### 2.4 경로를 고른 뒤: 안내 모드

1. **안내 모드로 바뀝니다.** 카드 목록이 접히고, 아래에 지금 할 일 한 줄만 남습니다. 예: "470 · 6분 뒤 도착 · 2분 뒤 나가세요". 지도는 내 위치와 지금 구간의 차량을 계속 한 화면에 담습니다.
2. **구간이 넘어가면 다음 차량으로 바뀝니다.** 버스에 타면 지도의 초점이 환승할 열차로 옮겨 갑니다. **탑승은 출퇴근과 같이 버튼 없이 시간으로 판단합니다.** 2026-11-11에 "탔어요 / 다음 차 탈게요" 버튼을 뺀 결정을 길찾기에도 그대로 적용합니다(2026-11-20 확인). 위치로 자동 판단하는 것은 나중입니다.
3. **놓치면 다시 계산합니다.** 탈 차를 놓치면 다음 차 기준으로 다시 계산합니다. 다른 후보가 더 빠르면 알려 줍니다.
4. **잠금화면으로 이어 갑니다.** 출퇴근 때처럼 iOS Live Activity와 Android Live Update로 잠금화면에 안내를 띄웁니다. 앱을 닫아도 언제 나가야 하는지 볼 수 있습니다.
5. **끝나면 정리합니다.** 목적지 근처에 도착하거나 사용자가 안내를 끝내면, 그동안 관측하던 노선(경기·인천 버스 포함)의 관측을 멈춥니다.

### 2.5 비용 원칙

- 지도 설계 2.6과 같습니다. 이미 받는 데이터는 보여 주고, 새로 받는 데이터는 사용자가 원할 때만 받습니다.
- 처음 여는 노선은 시간표 추정을 먼저 보여 주고, 실시간이 들어오면 바꿉니다.

## 3. 구조 [설계 판단]

### 3.1 하이브리드

- **경로 후보는 외부 경로 API에서 받습니다.** Betro는 그 후보를 "탈 수 있는 차" 기준으로 다시 계산하고 정렬합니다.
- **자체 경로 계산(RAPTOR 등)은 지금 만들지 않습니다.** 버스는 운행 시각 데이터가 없고(노선·정류장·모양만 있음), 정류장 사이 도보 링크와 환승 데이터도 없습니다. 직접 만들면 품질이 네이버·카카오보다 떨어집니다. 지하철은 열차별 시간표가 있으니 나중에 다시 볼 수 있습니다.

### 3.2 경로 엔진: TMAP 대중교통 API

- **1순위는 TMAP 대중교통 API(`POST apis.openapi.sk.com/transit/routes`)입니다.** 서울·경기·인천을 처음부터 다루려면 전국 커버리지가 필요합니다.
  - 요금: 종량제 후불, 경로 1건 0.88원. 무료 체험은 하루 10건이라 개발 시험용입니다.
  - 결과는 저장 후 24시간까지만 쓸 수 있습니다. 경로 결과는 길게 캐시하지 않습니다.
  - 같은 서비스에 프로젝트를 여러 개 만드는 것은 약관상 금지입니다.
- **보조는 서울시 대중교통환승경로 API(ws.bus.go.kr `pathinfo`)입니다.** 무료이고 공공누리 1유형입니다. 서울 버스 원본 ID를 줄 가능성이 커서, 승인되면 서울 구간의 매핑 대조용으로 씁니다. 활용신청은 아직 안 되어 있습니다(6장).
- **쓰지 않는 것**
  - ODsay: 무료가 하루 30건이고 약관상 비상업 용도만 허용합니다.
  - 카카오 대중교통: 정류장·노선 ID가 없습니다.
  - 네이버: 대중교통 길찾기 API가 없습니다.
- 엔진 호출은 Worker가 합니다. 키는 앱에 넣지 않습니다(MVP 설계 2장 실패 기준).

### 3.3 장소 검색: 카카오 로컬 API

- 키워드 검색과 주소 검색에 카카오 로컬 API를 씁니다. 좌표가 WGS84로 오고, 결과를 최대 45건까지 받을 수 있으며, 현재 위치 기준 정렬을 지원합니다.
- 호출은 Worker가 대신합니다. 결과는 서버에 저장하거나 캐시하지 않습니다(카카오 약관). 자동완성은 디바운스로 호출 수를 줄입니다.
- 결과가 모자랄 때의 보조는 네이버 지역 검색입니다(결과 최대 5건).

### 3.4 외부 경로를 Betro 경로로 바꾸기

- TMAP의 버스 노선 ID와 정류장 ID는 TMAP 자체 체계로 보입니다. 서울 버스 ID(`busRouteId`, `stId`, `arsId`)와 형식이 다릅니다.
- 그래서 TMAP 구간을 Betro 구간으로 바꿀 때 다음 단서로 맞춥니다.
  - 버스: 노선 이름(예: "간선:400")과 지역으로 `bus_route`를 찾습니다. 승·하차 정류장은 좌표와 이름으로 그 노선의 `bus_route_stop`(좌표, `ars_id`, `seq` 있음)에서 찾습니다. 순환 노선은 같은 정류장이 두 번 나오므로 진행 방향으로 고릅니다.
  - 지하철: 노선 코드와 역 이름으로 `station_crosswalk`를 찾습니다(`packages/transit-static/src/crosswalk/normalize-name.ts`의 정규화). 방향은 `apps/server/src/ref/subway.ts`의 `findDirection`으로 정합니다.
- 바꾼 결과는 출퇴근과 같은 `Route` 형태(`packages/commute/src/plan.ts`)로 만들고 `estimateRoute`에 넣습니다.
- **Betro ID로 못 바꾼 구간은 TMAP이 준 소요시간(`sectionTime`)으로 계산하고, 그 구간에 "추정"을 표시합니다.** 지금 코드는 매핑이 안 된 구간이 하나라도 있으면 경로 전체 ETA가 null이 됩니다(`packages/commute/src/sources/assemble.ts`의 `adapterOf`). 이 부분을 바꿔야 합니다.
- 출퇴근 대안 제안에 쓰는 `suggestionOf`(`packages/commute/src/session/content.ts`)는 첫 구간이 추정인 후보를 버립니다. 길찾기 정렬에서는 버리지 말고 추정임을 표시합니다.

### 3.5 첫 작업: 매핑 비율 측정

- 구현 전에 대표 여행 50건쯤을 TMAP으로 받아, 구간 중 Betro ID로 바뀌는 비율을 잽니다. 여행은 서울·경기·인천을 섞고, 마을버스와 광역버스를 포함합니다.
- 버스·지하철 구간의 **90% 이상**이 바뀌면 이 설계대로 갑니다. 못 미치면 결과를 들고 사용자와 다시 정합니다. 90%는 설계자가 정한 기준입니다.
- "바뀐다"는 Betro의 정적 ID(노선, 승·하차 정류장 또는 역, 방향)로 바뀐다는 뜻입니다. 실시간이 있는지는 따지지 않습니다. **[설계 판단]**
- 분모는 Betro가 다루는 수단의 구간입니다. 서울·경기·인천 버스(마을버스 포함)와 실시간 API가 있는 수도권 지하철이 여기에 들어갑니다. 공항버스, 고속·시외버스, 일반 열차, 항공, 해운, 실시간 API가 없는 경전철은 분모에서 뺍니다. 이런 구간은 TMAP 소요시간으로 "추정" 표시합니다. **[설계 판단]**
- **전체 측정은 경기·인천 실시간 연결(지도 설계 8장 순서 2)이 끝난 뒤에 합니다.** 그 전에는 서울을 벗어나는 노선의 정적 데이터가 없어 기준을 넘을 수 없기 때문입니다. 서울 안 여행만으로 하는 예비 측정은 먼저 해도 됩니다. **[설계 판단]**

### 3.6 실시간과 비용

- 후보 하나의 첫 버스 구간을 "탈 수 있는 차"로 계산하려면, 그 노선의 도착정보가 필요합니다. 지금 실행기는 노선 하나에 `getArrInfoByRouteAll` 1건을 씁니다.
- 후보 5개에 버스 노선이 2개씩이면 검색 한 번에 최대 10건입니다. `dev` 한도(하루 1,000건)에서는 검색 수십 번이면 바닥납니다. 그래서 다음을 지킵니다.
  - 같은 노선의 도착정보는 짧은 시간 동안 여러 검색이 나눠 씁니다. 지도 설계 4.3의 관측 요청과 같은 방식입니다.
  - 예산은 설정값입니다. 우선순위는 출퇴근 세션 > 길찾기·관측 요청 > 지도용 상시 관측입니다.
  - 한도를 다 쓰면 시간표 추정으로 바뀌고 화면에 표시합니다.
- 지하철은 전 노선을 이미 수집하므로 추가 호출이 거의 없습니다.

### 3.7 안내 모드와 잠금화면

- 안내 모드의 잠금화면은 출퇴근 세션 실행기를 다시 씁니다. 다만 예약(요일·시각)이 없는 **한 번짜리 세션**입니다. 세션 입력 API는 출퇴근과 같은 `end` 하나만 씁니다.
- **한 기기에서 세션은 한 번에 하나입니다.** **[설계 판단]**
  - 출퇴근 세션이 도는 중에 안내를 시작하면, 출퇴근 세션을 끝낼지 먼저 묻습니다.
  - 안내 중에 출퇴근 예약 시각이 되면 안내가 이깁니다. 그날 그 출퇴근 자동 시작은 건너뛰고, 건너뛴 사실을 기록합니다.
- 서버에는 경로 구간(노선, 승·하차 정류장, 방향)만 보냅니다. **출발지와 목적지의 좌표·이름은 서버에 저장하지 않습니다**(MVP 설계 2장 실패 기준, 5.2).
  - 다만 검색과 경로 요청 때는 좌표가 Worker를 거쳐 TMAP과 카카오로 갑니다. 이 사실은 13 데이터 출처(또는 개인정보 안내)에 적습니다.
  - Worker 로그에도 좌표와 검색어를 남기지 않습니다.
- 안내 정확도도 출퇴근과 같은 방식으로 기록합니다(MVP 설계 5.4). 출퇴근 세션과 구분할 수 있게 표시합니다.

## 4. 범위 밖

- 걷는 동안 경로 순위가 계속 바뀌며 알려 주는 기능. 안내 모드에서 놓쳤을 때 다시 계산하는 것(2.4의 3)만 넣습니다.
- 위치로 탑승을 자동 판단하는 기능.
- 자체 경로 계산.
- 출발 시각 예약("내일 10시 출발 기준"). 이번에는 "지금 출발" 하나입니다. **[설계 판단]**
- 도보 길 안내(턴바이턴). 걷는 길은 지도에 선으로만 그립니다.

## 5. 실패로 보는 것

- "탈 수 있어요"라고 했는데, 계산대로 걸어가면 그 차를 놓칩니다.
- 매핑하지 못한 구간이 있는데 그 경로가 "실시간"으로 보입니다.
- 출발지·목적지의 좌표나 이름이 서버(D1, R2, 로그)에 남습니다.
- 안내를 끝냈는데 관측이나 잠금화면이 남아 있습니다.
- 외부 API 키가 앱에 들어갑니다.

## 6. 사용자가 해야 할 일 (구현 전)

| 공공데이터포털에서 "서울특별시_대중교통환승경로 조회 서비스" 활용신청(운영 키 계정으로) | 보조 엔진, 매핑 대조 |

**약관 답변을 기다리는 동안** 매핑 측정, Worker, 화면은 함께 만듭니다. 길찾기를 앱 업데이트로 공개하는 일만 SK와 카카오의 서면 답변이 온 뒤에 합니다. 답변이 "안 된다"이면 그 결과를 들고 사용자와 엔진이나 검색 API를 다시 정합니다. **[설계 판단]**

## 8. 구현자에게 맡기는 것

- 후보 수(TMAP `count` 1~10), 결과 카드 정렬의 동점 처리
- 매핑 알고리즘의 세부(이름 정규화, 좌표 허용 거리, 순환 노선 처리)
- 도보 시간 계산(TMAP 도보 구간 시간을 쓸지, Betro 기본값을 쓸지)

- "목적지 근처 도착"을 판단하는 방법
- 최근 검색어를 기기에 저장할지
- 화면 문구(문구 키 관리, MVP 설계 5.10)

## 9. MVP 설계에 반영할 곳

지도 설계 9장의 표와 함께 반영합니다. 이 문서에서 더하는 것은 다음과 같습니다.

| 위치 | 바꿀 내용 |
|---|---|
| 2장 목표 | "현재 위치에서 목적지까지 경로를 찾고, 지금 탈 수 있는 차 기준으로 비교한다"를 더합니다 |
| 3장 결정 표 | 길찾기(범위 안, 서울·경기·인천), 경로 엔진(TMAP + 서울 pathinfo 보조), 장소 검색(카카오 로컬)을 더합니다 |
| 4.1 화면 | 길찾기 검색, 결과, 안내 모드 화면을 더합니다. Figma에 먼저 그립니다 |
| 5.1 전체 그림 | Worker에 길찾기 API(장소 검색, 경로 후보와 재계산)를 더합니다 |
| 7장 출시 기준 | 길찾기는 1차 출시 기준에 넣지 않습니다. 업데이트로 붙일 때의 기준은 2.1을 따릅니다 |
| 8장 작업 순서 | 지도 → 경기·인천 실시간 연결 → 길찾기 |

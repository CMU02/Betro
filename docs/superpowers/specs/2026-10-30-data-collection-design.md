# Betro 데이터 수집 설계

- 작성일: 2026-10-30
- 상태: 초안 (사용자 검토 전)
- 근거 자료: [`docs/research/2026-10-30-data-sources.md`](../../research/2026-10-30-data-sources.md) (이 문서의 사실 근거와 출처 링크는 모두 여기에 있습니다)

이 문서에서 **[사용자 결정]**은 사용자가 직접 정한 것이고, **[설계 판단]**은 설계자가 정한 것입니다. 설계 판단은 구현 중에 근거가 생기면 바꿔도 됩니다.

---

## 1. 목적

Betro는 서울의 지하철과 버스가 지금 어디를 달리고 있는지를 네이버 지도 위에 보여주는 모바일 앱입니다. 레퍼런스는 Mini Tokyo 3D이고, 목표는 그보다 높은 시각적 완성도입니다.

화면의 완성도는 결국 **차량이 얼마나 자연스럽게 움직이느냐**에 달려 있습니다. 그런데 공공 API는 그대로 쓰면 자연스러운 움직임을 만들 수 없습니다.

- 지하철 실시간 API는 좌표를 주지 않고 "어느 역에 진입·도착·출발했는지"만 줍니다. 게다가 실제보다 수십 초 늦습니다.
- 버스 API는 좌표를 주지만 약 20초 간격으로만 바뀝니다.

그래서 이 문서가 설계하는 데이터 수집 계층의 일은 다음과 같습니다. **역 사이·정류소 사이 위치를 계산(보간)하는 엔진이 필요로 하는 재료를 정확하고, 끊기지 않고, 공공 API 한도 안에서 모아 두는 것**입니다. 재료는 네 가지입니다: 선로와 노선의 모양, 시간표, 실시간 상태, 그리고 그동안 쌓인 이력입니다.

## 2. 목표, 범위 밖, 실패 기준

### 목표

1. 서울 지하철 실시간 API가 제공하는 19개 노선 전체와 서울 시내버스 396개 노선 전체의 실시간 상태를 서버 한 곳에서 모은다.
2. 보간 엔진이 쓸 정적 참조 데이터(역·정류소 좌표, 선로·노선 모양, 시간표, 서로 다른 데이터셋의 ID를 잇는 대응표)를 만들고 주기적으로 갱신한다.
3. 출처마다 다른 형식(코드값, 시각 표기, 거리 단위, 좌표 필드 이름, 오류 응답 형태)을 하나의 내부 데이터 모델로 정규화한다.
4. 모든 관측을 이력으로 저장해 구간 주행시간과 지연 패턴을 학습할 재료로 쓴다(공공 API는 과거 데이터를 제공하지 않음).
5. API 한도를 넘지 않도록 호출량을 서버가 스스로 관리하고, 한도 승인 전후에 다르게 동작한다.
6. 데이터 품질(신선도, 매칭률, 누락)을 숫자로 볼 수 있다.

### 범위 밖 (이 문서에서 다루지 않음)

- **보간 엔진 자체**: 위치 계산 알고리즘은 다음 설계 문서에서 다룹니다. 이 문서는 보간 엔진에 넘기는 데이터 계약(10장)까지만 정합니다.
- **앱으로 데이터를 내려주는 방식**: WebSocket/SSE 같은 전송 방식, 압축, 뷰포트별 구독은 배포 설계 문서에서 다룹니다.
- **렌더링**: 네이버 지도 위 마커, 노선 그리기, 3D 건물 표현.
- **마을버스, 경기·인천 면허 버스**: 1차 범위가 아닙니다. 마을버스가 위치 API에 들어 있는지조차 아직 확인되지 않았습니다. **[설계 판단]**
- **실시간 API에 없는 노선**: 김포골드라인, 인천 1·2호선, 의정부·용인 경전철, 교외선. **[설계 판단]**
- 사용자 계정, 즐겨찾기, 알림 같은 앱 기능.

### 실패로 보는 것

기술적으로 돌아가더라도 다음과 같으면 실패입니다.

- 차량이 역에서 역으로 순간이동하거나, 멈췄다가 튀거나, 뒤로 가는 모습이 눈에 띄게 자주 보인다. 수집 계층의 책임은 이런 현상의 원인이 되는 데이터 결함(누락, 순서 뒤바뀜, 잘못된 매칭)을 걸러내고 표시하는 것입니다.
- 서버 장애나 한도 초과로 데이터가 끊기는데, 그 사실을 아무도 모른다.
- API 이용 약관이나 라이선스(공공누리, ODbL, 네이버 Maps 약관)를 어겨서 키가 막히거나 서비스를 내려야 한다.
- 공공 API 키가 앱에 들어가서 노출된다.

## 3. 정해진 결정

| 항목 | 결정 | 구분 |
|---|---|---|
| 제품 형태 | 모바일 앱이 메인, 웹은 랜딩 페이지 | 사용자 결정 |
| 지도 | 네이버 지도 (무조건) | 사용자 결정 |
| 범위 | 서울 지하철 전 노선 + 서울 시내버스 전체 | 사용자 결정 |
| 웹의 역할 | 앱 소개 페이지만. 실시간 데이터 시연을 넣지 않음 | 사용자 결정 |
| API 한도 승인 시점 | 앱을 스토어에 올린 뒤 활용사례를 등록해 신청 | 사용자 결정 (웹에 시연을 넣지 않으므로) |
| 상업적 이용 | 아직 정하지 않음. 비상업 전제로 진행하고, 사업화 전에 서울시에 버스 데이터 이용 조건을 문의 | 사용자 결정 |
| OSM 라이선스 | ODbL 의무(출처 표시, 요청 시 가공한 선로 데이터 공개)를 지킴 | 사용자 결정 |
| 수집 구조 | 서버 한 곳이 공공 API를 모으고 앱은 서버만 바라봄 | 설계 판단 (호출량과 키 보안 때문에 사실상 필수) |
| 서버 스택 | 기존 `apps/server` (Bun + Fastify)에 수집기를 둠 | 설계 판단 (기존 스택 재사용) |
| 지하철 노선 정의 | 실시간 API가 응답하는 19개 노선 전체, 서울 밖 구간 포함 | 설계 판단 |
| 선로 모양 출처 | OpenStreetMap | 설계 판단 (신규 노선까지 반영된 유일한 출처) |
| 네이버 결과 데이터 | 저장하지 않음. 모양과 좌표는 공공데이터와 OSM으로만 만듦 | 설계 판단 (Maps 약관이 결과 데이터 저장·DB화를 금지) |
| 보간을 어디서 하나 | 서버가 차량 상태를 추정(어느 열차 편인지, 선 위 거리, 속도, 기준 시각)하고, 앱은 미리 받아 둔 선로·노선 모양 위에서 매 프레임 움직임만 계산 | 설계 판단 (아래 설명) |
| 시간 | 내부는 UTC epoch ms로 저장, 원본 KST 문자열도 보존 | 설계 판단 |
| 좌표계 | 내부는 WGS84(EPSG:4326)로 통일 | 설계 판단 |

19개 노선은 1~9호선, 경의중앙선, 공항철도, 경춘선, 수인분당선, 신분당선, 우이신설선, 서해선, 경강선, GTX-A, 신림선입니다.

**보간 위치를 이렇게 나눈 이유**: 네이버 지도 마커를 부드럽게 움직이려면 기기에서 매 프레임 좌표를 계산해야 합니다. 서버가 초당 수십 번 좌표를 보내는 건 비현실적입니다. 반면 열차번호 매칭, 지연 추정, 이력 학습은 무겁고 모든 사용자에게 같은 결과이므로 서버에서 한 번만 하는 게 맞습니다. 그래서 서버는 "이 열차는 이 시각에 이 선의 몇 m 지점을 초속 몇 m로 지나고 있다"까지 계산하고, 앱은 그 사이를 이어 그립니다.

이 결정의 결과로 **선로 모양과 선 위 역 위치(OSM 파생 데이터)가 앱 사용자에게 배포됩니다.** 노선을 지도에 그리려면 어차피 필요한 데이터입니다. 그래서 ODbL 의무(출처 표시, 요청 시 파생 데이터 제공)를 지키는 것을 전제로 합니다(4.5절, 12장).

## 4. 조사로 확인된 제약

자세한 근거는 조사 보고서에 있습니다. 설계에 직접 영향을 주는 것만 모았습니다.

### 4.1 호출 한도가 출시를 막는다

| 출처 | 기본 한도 | 필요한 양(추정) | 한도를 푸는 방법 |
|---|---|---|---|
| 서울 열린데이터광장 실시간 지하철 키 | 하루 1,000건 | 20초 주기 기준 하루 약 8.6만 건 | 활용사례(갤러리)에 실제 동작하는 서비스(스토어 앱 또는 실제 웹 URL)를 등록해 승인받으면 "호출 제한 없음" |
| data.go.kr 서울 버스위치(15000332) | 개발계정 하루 1,000건 | 30초 주기 기준 하루 약 114만 건 | 운영계정으로 전환 후 활용사례 등록과 트래픽 증설 신청. 상한은 공개되지 않음. 초당 30TPS 언급 있음 |
| data.go.kr 서울 노선정보(15000193) | 개발계정 하루 1,000건 | 하루 1회 배치 약 800건 | 개발계정으로 가능하지만 빠듯함 |

결론: **승인 전에는 전체 규모로 돌릴 수 없습니다.** 수집기는 처음부터 "승인 전 모드"와 "승인 후 모드"를 설정으로 바꿀 수 있어야 합니다(7.4절).

### 4.2 데이터 형태의 함정

- 상류 API는 모두 HTTP만 응답합니다. HTTPS는 시간 초과입니다. 서버만 HTTP로 수집하고, 앱에는 HTTPS로 내려줘야 합니다.
- 지하철 realtimePosition은 한글 노선명(UTF-8 퍼센트 인코딩 필수)으로 조회합니다. 오류여도 HTTP 200이 오고, 성공과 실패의 JSON 구조가 다릅니다.
- `updnLine`이 API마다 다릅니다("0"/"1"과 "상행"/"하행"/"내선"/"외선").
- `recptnDt`는 KST(타임존 표기 없음)이고, 대부분의 노선에서 열차별 마지막 상태 변화 시각입니다. 신분당선만 응답 시각입니다.
- 실시간 지하철 정보는 실제보다 약 36~87초 늦게 나타난다는 서드파티 측정이 있습니다.
- 버스 `getBusPosByRtid`의 `sectDist`, `fullSectDist`는 km이고, `getStaionByRoute`의 `fullSectDist`는 m입니다. `rtDist`와 `nextStId`는 차량 위치를 계산하는 데 쓸 수 없습니다.
- 버스 `sectOrd`는 차량이 마지막으로 지난 정류소의 `seq`와 일치합니다. 순환 노선은 같은 정류소가 두 번 나오므로 정류소 ID가 아니라 순번으로 이어야 합니다.
- 시간표에서 `00:00:00`은 "값 없음"이고, 24시·25시는 다음 날 0시·1시입니다.

### 4.3 ID가 데이터셋마다 다르다

- 실시간 지하철의 역 ID(`statnId`)를 좌표 데이터에 바로 잇는 공식 대응표가 없습니다. "statnId 뒷자리 = FR_CODE" 규칙은 1호선 코레일 구간과 지선에서 깨집니다.
- 실시간 열차번호(`trainNo`)와 시간표 열차번호를 잇는 규칙이 노선마다 다릅니다.
  - 1호선: K/S 접두를 떼고 4자리로 0을 채움
  - 3·5~8호선: 같음
  - 4호선: 일부에 K 접두
  - 9호선: C(일반)/E(급행) 접두
  - 코레일 노선: K 접두
  - 공항철도, 우이신설: 같음
  - 2호선 본선: 끝 3자리 앞에 2를 붙이면 맞음(교차 검증 전). 성수에서 번호가 바뀜
  - 신분당선: 대응 규칙 없음. 실시간 번호가 차량 단위 ID로 보임
  - GTX-A: 대응 규칙 미확인
- 이 규칙들은 공식 보장이 없는 관행이라 언제든 깨질 수 있습니다.

### 4.4 시간표 출처가 노선마다 다르고 낡을 수 있다

| 노선 | 1차 출처 | 열차별 시각 여부 | 비고 |
|---|---|---|---|
| 1~9호선 | 서울교통공사 CSV (data.go.kr 15098251) | 열차코드 = 열차 1편 | 평일/토/휴일. 2026-09 판 |
| 2호선 본선 보정 | OA-22750 getTrainSch | 있음 | 기준일 2025-06으로 오래됨 |
| 코레일 5개 노선(경의중앙, 수인분당, 경춘, 서해, 경강) | korail.com 시각표 게시판 XLSX | 있음 | 평일/휴일만 있음 |
| 우이신설, 신림, 신분당 | KRIC 파일 id=900 | 있음(형식이 기관마다 다름) | 갱신 예정 없음 |
| 공항철도 | KRIC id=900 + 공식 직통 시각표 | 직통은 열차번호 없음 | 2026-10-23 개정이 반영 안 됨 |
| GTX-A | KRIC Open API subwayTimetable | 있음(제3자 실측) | 파일에는 없음 |

한국용 GTFS 피드는 찾지 못했습니다.

### 4.5 라이선스

- 서울시와 data.go.kr 데이터는 공공누리 1유형(출처 표시, 상업적 이용 가능)입니다. 다만 api.bus.go.kr 소개 페이지에는 "상업적으로 이용 불가"라는 문구가 있어 상충합니다.
- OSM 선로 데이터를 가공한 데이터베이스를 남에게 제공하면 ODbL(동일조건 공유)이 적용됩니다. 렌더링 결과물은 자유입니다. OSM 데이터와 비OSM 데이터를 키로만 연결하면 별개 데이터베이스로 볼 수 있지만, 같은 지역에서 같은 유형의 데이터(예: 선로)는 전부 OSM이거나 전부 비OSM이어야 합니다.
- 네이버 Maps 약관은 지도 결과 데이터(좌표, 경로 등)의 저장과 DB화를 금지합니다.

**[설계 판단]** 수집기는 계속 켜져 있는 프로세스여야 합니다. 20초 주기 폴링은 서버리스 함수나 분 단위 cron으로는 할 수 없습니다. 어디에 호스팅할지는 구현하는 사람이 정합니다(14장). 단, 다음 두 가지는 지켜야 합니다.

- **폴링은 한 번에 한 인스턴스만 합니다.** 여러 인스턴스가 동시에 폴링하면 한도가 배로 줄어듭니다. 배포 중에 옛 서버와 새 서버가 겹치는 순간도 포함입니다. 그래서 단순히 "인스턴스를 하나만 띄운다"에 기대지 말고, DB 임대(lease) 같은 리더 잠금을 둬서 잠금을 가진 프로세스만 폴링하게 합니다. 호출 카운터도 프로세스가 재시작돼도 이어지도록 DB에 둡니다.
- **호스팅 지역을 확인합니다.** 현재 `packages/infra/alchemy.run.ts`는 서버를 Prisma Compute `us-east-1`에 배포하게 되어 있습니다. 한국 공공 API가 해외 IP에서 정상 응답하는지는 확인하지 않았습니다. 0단계에서 실제 배포 위치로 호출해 보고, 막히면 국내 지역으로 옮깁니다.

## 6. 정적 데이터 수집

정적 데이터는 배치 작업으로 받아서 검증한 뒤 참조 DB에 넣습니다. 모든 배치는 **받은 원본 파일을 그대로 보관**하고(재현과 비교용), 원본 해시가 이전과 같으면 다시 적재하지 않습니다.

### 6.1 지하철 역과 대응표 (가장 먼저 만들어야 함)

실시간 상태를 지도 위 위치로 바꾸는 첫 단계라서 가장 중요합니다.

**입력**
- 실시간도착_역정보 xlsx (OA-12764 첨부, 월 단위로 새 판이 올라옴): `SUBWAY_ID`, `STATN_ID`, `STATN_NM`, 호선이름. 19개 노선 696개 역.
- 역사마스터 `subwayStationMaster` (OA-21232): `BLDN_ID`, `BLDN_NM`, `ROUTE`, `LAT`, `LOT`. 784건. 노선별 역 레코드 단위.
- 역 검색 `SearchInfoBySubwayNameService` (OA-121): `STATION_CD`, `STATION_NM`, `LINE_NUM`, `FR_CODE`.
- 보조: 서울교통공사 1~8호선 역 좌표 CSV (15099316), 전국도시철도역사정보표준데이터 (15013205).

**출력: Betro 자체 역 대응표 `station_crosswalk`**

| 필드 | 설명 |
|---|---|
| `statn_id` | 실시간 API의 역 ID (10자리 문자열). 런타임 조인 키 |
| `subway_id` | 노선 ID (예: 1002) |
| `line_key` | Betro 내부 노선 키 |
| `station_cd` | OA-121 STATION_CD (시간표 조인용) |
| `fr_code` | 외부 역 코드 |
| `bldn_id` | 역사마스터 ID |
| `name_canonical` | 대표 역명 |
| `name_aliases` | 출처별 역명 표기 목록 (서울/서울역, 시우/원곡 등) |
| `lat`, `lng` | 좌표 (WGS84) |
| `coord_source` | 좌표 출처 |
| `osm_stop_node_id` | 선로 위 정차 지점과 연결용 (6.2절) |
| `match_method` | 자동(같은 노선), 자동(공용역), 수동 별칭 중 무엇으로 맞췄는지 |

**규칙**
- 조인은 노선 그룹 안에서 역명으로 먼저 하고, 실패하면 공용역 레코드, 그다음 수동 별칭 표로 합니다. 조사에서 이 방식으로 696개 전부 좌표를 얻었습니다(교차 검증 전).
- 수동 별칭 표는 코드 저장소에 파일로 두고 리뷰를 거쳐 바꿉니다.
- **매칭 안 된 역이 하나라도 있으면 배치가 실패**하고 경고를 냅니다. 새 xlsx 판이 올라오면 이전 판과의 차이(추가·삭제·개명)를 보고서로 남깁니다.
- 실시간 응답에 대응표에 없는 `statnId`가 나오면 그 관측은 버리지 말고 "미매칭"으로 표시해 저장하고 지표에 셉니다.

### 6.2 선로 모양

**입력**: OSM Overpass API에서 서울·수도권 범위의 `route=subway`, `route=train`, `route=light_rail` relation과 소속 way, stop 노드.

**처리**
1. 노선별·방향별로 way를 이어 하나의 연속된 선(폴리라인)을 만듭니다. 갈라지는 구간(2호선 성수지선·신정지선, 경의중앙선 지선, 5호선 마천·하남 갈래, 1호선 여러 갈래 등)은 별도의 선으로 만듭니다.
2. 대응표의 역 좌표를 각 선 위로 투영해 **선의 시작점부터 그 역까지의 거리(m)**를 구합니다. 보간 엔진은 이 거리를 기준으로 위치를 계산합니다.
3. 역 투영점과 원래 좌표의 거리가 기준값(예: 150m)을 넘으면 경고합니다. OSM 데이터 오류나 잘못된 매칭을 잡기 위해서입니다.
4. 선의 길이, 역 순서, 역간 거리를 검증합니다. 역 순서가 대응표와 다르면 실패입니다.

**출력**: `track_shape`(노선, 갈래, 방향, 좌표 목록, 총길이), `track_station`(선, 역, 선 위 거리).

**라이선스 [설계 판단]**: 선로 모양은 전부 OSM에서만 가져옵니다. 비OSM 선로 데이터와 섞지 않습니다. 앱에 내려보내는 선로 데이터에는 OSM 출처를 표시합니다. 역 좌표를 OSM 선로에 투영한 결과(`track_station`)가 ODbL 파생 데이터인지는 법률 검토 항목입니다(15장).

**갱신**: 월 1회 또는 수동. 새 추출본과 기존 데이터의 차이가 크면(선 길이 1% 이상 변화 등) 자동 적용하지 않고 사람이 확인합니다.

### 6.3 시간표

시간표는 출처별 어댑터가 각자 형식을 읽어서 **하나의 공통 모델**로 바꿉니다.

**공통 모델**
- `trip`: 열차 1편. `line_key`, `service_day`(평일/토요일/휴일), `direction`, `timetable_train_no`(출처의 원래 번호), `express`(일반/급행/특급/직통), `origin`, `destination`, `source`, `source_version`(기준일).
- `stop_time`: 정차 1회. `trip`, `seq`, `statn_id`(대응표 거쳐서), `arrive_sec`, `depart_sec`(서비스일 0시 기준 초, 24시 이후는 86,400 이상), 둘 중 하나는 비어 있을 수 있음.

**출처별 어댑터**

| 어댑터 | 대상 | 주의점 |
|---|---|---|
| 서울교통공사 CSV | 1~9호선(코레일 직결 구간 포함) | cp949. `00:00:00`은 null. 역사코드 앞자리 0 유지(문자열로 읽기). (호선, 요일, 열차코드)가 1편 |
| OA-22750 getTrainSch | 2호선 본선 보정, 신분당선 회차 | 기준일이 오래됨. 서울교통공사 CSV와 비교해서 차이를 보고 |
| korail.com XLSX | 경의중앙, 수인분당, 경춘, 서해, 경강, 1호선 코레일 | 평일/휴일 두 시트. 토요일은 휴일 시간표로 간주 **[설계 판단, 공식 확인 필요]** |
| KRIC id=900 XLSX | 우이신설, 신림, 신분당(보조), 공항철도 일반 | 기관마다 칸 구분 형식이 다름(`+`, `-`, `,`, `/`). "운행시격" 텍스트만 있는 노선은 시간표로 쓸 수 없음 |
| KRIC subwayTimetable API | GTX-A | 역 단위 조회라 역마다 호출 후 열차번호로 묶어야 함 |
| 공항철도 직통 시각표 | 공항철도 직통 | 열차번호 없음. 출발 시각 슬롯으로만 매칭 |

**검증 (배치마다)**
- 모든 `stop_time`의 역이 대응표에 있어야 함.
- 한 열차 안에서 시각이 줄어들면 안 됨(24시 넘김 처리 후).
- 역간 소요시간이 같은 구간 다른 열차의 중앙값보다 3배 이상 길거나 1/3 미만이면 경고.
- 출처별 기준일을 기록하고, 기준일이 실제 개정일보다 오래된 출처는 지표로 표시.

**시간표 신선도 [설계 판단]**: 시간표는 낡을 수 있다고 가정합니다. 그래서 보간 엔진은 시간표를 "정답"이 아니라 "사전 정보"로 쓰고, 이력에서 학습한 실제 구간 주행시간(9.3절)을 함께 씁니다. 수집 계층은 출처별 기준일과 실제 관측과의 차이를 지표로 내서, 어느 시간표가 낡았는지 보이게 합니다.

**갱신 [설계 판단]**
- 공공 포털(data.go.kr, 서울 열린데이터광장, KRIC)의 파일과 API는 자동으로 받습니다. 서울교통공사 CSV는 주 1회 새 판을 확인하고, 나머지는 월 1회 확인합니다.
- korail.com 시각표 게시판과 공항철도 직통 시각표 페이지는 자동 수집 약관을 확인하지 못했습니다. 그래서 **사람이 파일을 받아서 넣는 방식**으로 합니다. 서버는 넣어진 파일의 해시 비교와 검증만 합니다. 대신 신선도 지표에 "마지막으로 넣은 지 30일이 지났거나, 관측과 시간표의 차이가 커지면 사람에게 갱신을 요청하는 경보"를 둡니다. 약관상 자동 수집이 허용된다고 확인되면 자동화합니다.

### 6.4 열차번호 대응 규칙

실시간 `trainNo`를 시간표 `trip`에 잇는 규칙을 **노선별로 바꿔 끼울 수 있는 함수**로 만듭니다(4.3절의 규칙들). 규칙은 코드로 두고 테스트 데이터(실제 응답 표본)로 검증합니다.

- 규칙으로 못 잇는 열차(신분당선, 시간표에 없는 9xxx 열차 등)는 "시간표 없음" 상태로 넘깁니다. 이때 보간 엔진은 구간 평균 주행시간으로 대신 계산합니다.
- 2호선 본선은 성수에서 번호가 바뀝니다. 번호가 바뀐 같은 열차를 이어 붙이는 일은 보간 엔진의 몫이지만, 수집 계층은 "번호 변경 후보"(같은 역, 같은 방향, 짧은 시간 간격에서 한 번호가 사라지고 다른 번호가 나타남)를 관측 이벤트에 표시합니다.
- 노선별 매칭률(관측된 열차 중 trip에 이어진 비율)을 지표로 내고, 기준값 아래로 떨어지면 경고합니다. 규칙이 깨졌다는 신호입니다.

### 6.5 버스 노선, 정류소, 노선 모양

**입력**
- 노선 목록: `getBusRouteList`는 전체 목록을 한 번에 주지 않습니다. 열린데이터광장의 노선 엑셀(OA-1095 첨부, 월 단위)에서 `busRouteId` 목록을 얻습니다.
- 노선별 정류소: `getStaionByRoute` (seq, station, gpsX/gpsY, fullSectDist(m), routeType 등)
- 노선별 모양: `getRoutePath` (좌표 목록. 정류소 경계 정보 없음)

**처리**
1. 노선마다 정류소를 순서대로 노선 모양 위에 투영해서, 노선 모양을 정류소 구간으로 나눕니다. 결과는 구간마다 (시작 seq, 끝 seq, 모양 위 시작 거리, 끝 거리)입니다.
2. 투영이 뒤로 가거나(정류소 순서와 모양이 맞지 않음) 정류소와 모양 사이 거리가 기준값(예: 80m)을 넘으면 경고합니다.
3. 모양에서 잰 구간 길이와 `fullSectDist`를 비교해 차이를 기록합니다.

**출력**: `bus_route`, `bus_route_stop`(노선, seq, 정류소, 좌표), `bus_route_shape`, `bus_route_segment`(구간과 모양 위 거리 범위).

**호출량**: 노선 396개 × 2개 오퍼레이션 = 하루 약 800건. 노선정보 API의 데이터가 새벽 5시에 갱신되므로 매일 05시 이후 1회 실행합니다. **[설계 판단]** 모든 노선을 매일 다시 받기보다는, 노선 엑셀이 바뀌었거나 7일이 지난 노선만 받아 호출량을 줄여도 됩니다.

## 7. 실시간 수집

### 7.1 지하철

**두 가지 소스**
- `realtimePosition`: 노선별 1회 호출(`0/999`), 19개 노선이면 1주기에 19회.
- `realtimeStationArrival/ALL`: 1회 호출로 전 노선의 역별 도착 정보(약 3,000행, 약 1.9MB). 열차번호, 역, 도착 코드(`arvlCd`), 생성 시각이 들어 있습니다.

**[설계 판단]** 어느 쪽을 주 소스로 할지는 정식 키로 직접 비교한 뒤 정합니다(13장 0단계). 비교 기준은 다음과 같습니다.

1. 같은 시점에 두 소스에서 보이는 열차 집합이 얼마나 같은가
2. 열차별 상태 변화가 어느 쪽에서 먼저 보이는가
3. 경로형 ALL 호출이 정식 키에서 정말 전량(1,000행 제한 없이)을 주는가

만약 ALL 하나로 충분하다면 1주기 1회로 끝나므로, 승인 전 한도(하루 1,000건) 안에서도 약 90초 주기로 전체를 볼 수 있습니다.

**폴링 주기**: 두 소스가 바뀌는 간격이 약 20초로 관측됐습니다. 승인 후 기본값은 20초로 두고 설정으로 바꿀 수 있게 합니다.

**변화 감지**: 같은 열차의 상태가 이전 폴링과 같으면 새 관측 이벤트를 만들지 않습니다. 상태가 바뀐 경우만 "상태 전이 이벤트"를 만듭니다. 신분당선은 `recptnDt`가 응답 시각이라서, 서버가 상태 전이를 처음 본 시각을 따로 기록합니다.

### 7.2 버스

**호출**: `getBusPosByRtid`를 노선마다 1회. 396개 노선을 한 바퀴 도는 데 걸리는 시간이 곧 갱신 주기입니다.

**스케줄러 [설계 판단]**
- 토큰 버킷으로 초당 호출 수를 제한합니다. 기본값은 초당 10건(30TPS의 의미가 불명확하므로 여유를 둠). 설정으로 바꿀 수 있습니다.
- 노선마다 우선순위와 목표 주기를 둡니다.
  - 기본 목표 주기: 30초
  - 운행 종료 응답(headerCd 8)을 받은 노선: 다음 첫차 시각 근처까지 쉬거나 10분마다 확인
  - 이후 보간 품질 데이터가 쌓이면 배차 간격이 짧은 노선을 더 자주 부르는 식으로 조정
- 하루 호출 예산을 정하고(승인된 한도의 90% 등), 예산을 시간대별로 나눠 씁니다. 예산이 모자라면 주기를 늘려서 하루 끝까지 버팁니다. 한도는 KST 00시에 초기화됩니다.

**변화 감지**: 차량별로 `dataTm`이 이전과 같으면 새 관측을 만들지 않습니다.

**정규화 시 계산할 값**
- 차량 위치를 노선 모양 위 거리로 바꿉니다: `구간 시작 거리 + (sectDist / fullSectDist) × 구간 길이`. 구간은 `sectOrd`(마지막으로 지난 정류소의 seq)로 찾습니다.
- 노선 모양 위에 `gpsX/gpsY`를 투영한 거리도 따로 계산해 둡니다. 두 값이 크게 다르면 품질 플래그를 답니다.
- 같은 차량의 위치가 이전보다 뒤로 가면 "역행" 플래그를 답니다(드물지만 관측됨). 버리지는 않습니다.

### 7.3 공통 동작

- 모든 요청에 타임아웃(예: 10초)을 두고, 실패하면 지수 백오프로 재시도합니다. 한 노선의 실패가 다른 노선의 폴링을 막으면 안 됩니다.
- 원본 응답 본문은 그대로 압축해서 이력에 남깁니다(9.1절). 정규화 규칙에 버그가 있어도 나중에 원본에서 다시 계산할 수 있게 하기 위해서입니다.
- 키는 서버 환경변수로만 둡니다. 프로젝트의 `varlock` 스키마(`apps/server/.env.schema`)에 민감 값으로 추가합니다.
- 상류 요청의 User-Agent나 헤더에 개인정보(이메일 등)를 넣지 않습니다.

### 7.4 한도 모드

설정 하나로 모드를 바꿉니다.

| 모드 | 지하철 | 버스 | 용도 |
|---|---|---|---|
| `sample` | sample 키로 받을 수 있는 범위(행 5개) | 없음 | 형식 확인, 테스트 표본 수집 |
| `dev` (승인 전) | 하루 1,000건 안에서. 주 소스가 ALL이면 약 90초 주기 전체, 아니면 일부 노선 | 하루 1,000건 안에서 지정한 시험 노선 몇 개만 | 개발, 승인 전 출시 기간 |
| `prod` (승인 후) | 20초 주기 전체 | 승인된 한도에 맞춰 전체 | 서비스 |

모드와 상관없이 **서버가 스스로 호출 수를 세고**, 남은 예산이 0이 되면 그날은 더 부르지 않습니다. 지하철 API는 하루 한도 초과를 알리는 공식 오류 코드가 없으므로 자체 카운터가 유일한 안전장치입니다.

### 7.5 오류 분류

| 상황 | 판단 기준 | 처리 |
|---|---|---|
| 지하철 정상이지만 데이터 없음 | `code: INFO-200` | 운행 없음으로 처리. 단, 운행 시간대에 계속 나오면 인코딩·요청 오류 가능성으로 경고 |

| 버스 초당 한도 초과 | GW 코드 23, api.bus.go.kr 코드 8 | 백오프 후 토큰 버킷 속도를 낮춤 |
| 버스 운행 종료 | headerCd 8 | 그 노선을 쉼 |

## 8. 내부 데이터 모델 (정규화 결과)

정규화 계층의 출력이자 보간 엔진의 입력입니다. 필드 이름은 구현하는 사람이 정해도 되지만, 담는 정보는 아래를 지킵니다.

**지하철 관측 이벤트 `SubwayObservation`**
- 언제: `observed_at`(서버가 받은 시각), `source_at`(`recptnDt`를 UTC로 바꾼 값), `source_at_kind`(상태 변화 시각인지 응답 시각인지)
- 무엇: `line_key`, `raw_train_no`, `trip_id`(매칭됐으면), `match_status`(매칭, 시간표 없음, 번호 변경 후보)
- 어디: `statn_id`, `status`(진입/도착/출발/전역출발), `direction`(내부 통일 값), `destination_statn_id`
- 기타: `express`, `last_train`, `source`(realtimePosition 또는 ALL), `quality_flags`

**버스 관측 이벤트 `BusObservation`**
- 언제: `observed_at`, `source_at`(`dataTm`)
- 무엇: `route_id`, `veh_id`, `plain_no`, `bus_type`
- 어디: `sect_ord`, `shape_distance_m`(구간 비율로 계산), `gps_projected_distance_m`, `lat`, `lng`, `stopped`(stopFlag)
- 기타: `congestion`, `last_trip`(islastyn), `quality_flags`(역행, 두 거리값 불일치 등)

**최신 상태**: 노선별·차량별 마지막 관측을 메모리에 들고 있고, 보간 엔진이 언제든 읽을 수 있습니다.

## 9. 이력 저장

### 9.1 원본과 관측 이력

- **[설계 판단]** 원본 응답과 관측 이벤트는 DB가 아니라 **날짜별로 나눈 압축 파일**(예: 일 단위 NDJSON + zstd)로 저장합니다. 버스는 7천 대가 30초마다 갱신되면 하루 약 2천만 건이라, 참조 DB(SQLite)에 넣기에는 쓰기 부하가 큽니다.
- 보관 기간: 원본 30일, 관측 이벤트 1년 **[설계 판단, 저장 비용 보고 조정]**.

### 9.2 참조 DB

정적 데이터(6장의 출력)는 기존 Drizzle 설정(`packages/db`, 현재 `dialect: "turso"`인 libsql)에 넣습니다. 배치마다 버전을 매겨서, 문제가 생기면 이전 버전으로 되돌릴 수 있게 합니다.

### 9.4 앱 배포용 참조 데이터 묶음

앱이 보간하려면 선로·노선 모양, 선 위 역·정류소 위치, 노선 색 같은 참조 데이터를 기기에 들고 있어야 합니다(3장). 수집 계층은 참조 DB의 각 버전에서 **앱용 묶음 파일**을 만듭니다.

- 버전 번호가 붙어 있고, 앱은 자기 버전과 서버 최신 버전을 비교해 바뀐 묶음만 받습니다.
- 노선별로 나눠서, 일부만 바뀌면 그 노선만 다시 받게 합니다.
- 시간표 전체(약 42만 행)는 기기에 보내지 않습니다. 시간표 매칭과 지연 추정은 서버 몫이기 때문입니다.
- OSM에서 나온 데이터가 들어 있으므로 묶음에 ODbL 출처 표시를 포함합니다.
- 묶음 형식과 압축 방식은 구현하는 사람이 정합니다. 앱으로 전달하는 방식은 배포 설계 문서에서 정합니다.

### 9.3 파생 통계 (야간 배치)

보간 엔진이 쓸 학습 재료입니다.
- 지하철: 노선·방향·역 구간·요일 유형·시간대별 실제 주행시간과 정차시간의 분포(중앙값, 분위수). 시간표 대비 지연 분포.
- 지하철: 실시간 지연(실제 사건 시각과 API에 나타난 시각의 차이) 추정. 상태 전이가 API에 나타나는 지연을 노선별로 추정합니다.
- 버스: 노선·구간·요일 유형·시간대별 구간 통과시간 분포.

## 10. 보간 엔진에 넘기는 계약

보간 엔진(다음 설계 문서)은 서버 쪽 상태 추정과 앱 쪽 움직임 계산으로 나뉩니다(3장). 서버 쪽 상태 추정은 수집기와 같은 프로세스 안에서 돌며, 수집 계층에서 다음을 받는다고 가정할 수 있습니다. 앱 쪽은 9.4절의 묶음과 서버 쪽 추정 결과만 받습니다.

1. 참조 데이터: 역 대응표, 선로 모양과 선 위 역 위치, 시간표(trip, stop_time), 버스 노선 모양과 구간.
2. 실시간: 관측 이벤트 스트림과 최신 상태 조회.
3. 학습 재료: 파생 통계.
4. 모든 실시간 데이터의 시각은 UTC epoch ms이고, 지하철은 시각의 의미(`source_at_kind`)가 붙어 있습니다.
5. 매칭 실패, 역행, 미매칭 역 같은 품질 문제는 버려지지 않고 플래그로 붙어서 옵니다. 어떻게 처리할지는 보간 엔진이 정합니다.

## 11. 품질 지표

수집기는 다음 지표를 내보냅니다. 어떤 도구로 볼지는 구현하는 사람이 정합니다.

- 노선별 열차번호 매칭률
- 미매칭 역 수, 역행 버스 관측 수
- 시간표 출처별 기준일과 관측 대비 차이

## 13. 진행 단계

| 단계 | 내용 | 끝났다고 보는 기준 |
|---|---|---|
| 0. 키 신청과 확인 | 각 포털 키 신청(15장 사용자 할 일). 키가 나오면 정식 키로 재측정: ALL 전량 수신, 지하철 갱신 간격, 버스 `dataTm` 간격, 버스 거리 단위, 실제 배포 지역에서의 응답 | 키 발급, 재측정 결과를 조사 보고서에 추가 |
| 1. 역 대응표와 선로 | 6.1, 6.2절 | 19개 노선 전 역 매칭, 선로 투영 경고 검토 완료 |
| 2. 시간표 | 6.3, 6.4절 어댑터와 검증 | 전 노선 시간표 적재, 표본 기준 열차번호 매칭률 측정 |

| 4. 실시간 수집기 (`dev` 모드) | 7장, 8장, 9.1절 | 하루 동안 끊김 없이 수집, 지표 확인 |
| 5. 한도 승인 | 앱 스토어 출시 후 활용사례 등록으로 지하철·버스 한도 증설 신청 | 승인 |
| 6. `prod` 모드와 파생 통계 | 7.4절, 9.3절 | 전체 규모 수집 1주일 안정, 파생 통계 생성 |

**키가 없어도 시작할 수 있는 일**: 현재 키가 하나도 없습니다. 키 발급을 기다리는 동안 키 없이 받을 수 있는 데이터로 1~2단계를 먼저 진행합니다. 서울교통공사 시간표 CSV, KRIC id=900 파일, 실시간도착_역정보 xlsx, OSM이 해당합니다. 열린데이터광장 일반 인증키는 즉시 발급되므로 역사마스터와 OA-121도 바로 쓸 수 있습니다. 실시간 응답 형식은 sample 키와 공개된 응답 표본으로 정규화 코드를 먼저 만들고 테스트합니다. 3단계는 data.go.kr 키(자동 승인)가 나오는 대로 시작합니다. 1~3단계는 서로 독립적이라 동시에 진행할 수 있습니다.

**승인 전 기간의 위험**: 웹에 시연을 넣지 않기로 했으므로 한도 승인은 앱 스토어 출시 이후에야 신청할 수 있습니다. 그래서 출시 직후 승인이 나기까지(지하철 기준 심사 3~5일, 버스는 미공개) 앱은 `dev` 모드 한도로 돌아야 합니다. 지하철은 ALL 하나로 충분하다면 약 90초 주기로 전체를 볼 수 있습니다. 버스는 하루 1,000건이라 시험 노선 몇 개만 가능합니다. 출시 범위와 시점은 이 기간을 고려해 앱 설계에서 정합니다. TestFlight나 내부 테스트 트랙이 심사 대상으로 인정되는지는 확인하지 못했습니다(FAQ는 "앱스토어·구글플레이 등록"을 요구).

## 14. 구현하는 사람이 정할 것

- 수집기 호스팅 위치(계속 켜져 있는 단일 인스턴스면 됨)
- 수집기를 `apps/server` 안의 모듈로 둘지, 같은 저장소의 별도 워커 앱으로 둘지
- 이력 파일 형식과 저장 위치(로컬 디스크, 오브젝트 스토리지 등), 압축 방식
- 지표를 보는 도구
- 배치 작업 실행 방식(서버 내부 스케줄러, 외부 cron 등)
- 내부 데이터 모델의 필드 이름과 타입 세부
- 경고 기준값(150m, 80m, 3배 등)은 실제 데이터를 보고 조정

## 15. 확인해야 할 것과 사용자가 할 일

### 사용자가 할 일 (구현 전에 시작해야 함)

현재 상태: 키가 하나도 없음(2026-10-30).

1. 서울 열린데이터광장: 일반 인증키와 실시간 지하철 인증키 신청 (실시간 키는 즉시 발급이 아닐 수 있으므로 가장 먼저)
2. data.go.kr: 15000332(버스위치), 15000193(노선정보) 활용신청(개발계정). 발급 키로 실제 호출이 되는지 확인
3. KRIC 레일포털: 서비스키 발급, subwayTimetable 신청
4. 네이버 클라우드: Maps 애플리케이션 등록(Dynamic Map 체크, 앱 패키지명과 Bundle ID)

### 아직 확인 못 한 것

- 지하철 하루 1,000건이 키 단위인지 서비스별 단위인지, 승인 후 초당 제한이 있는지
- 버스 운영계정 증설 상한, 30TPS가 키별인지 서비스 전체인지
- api.bus.go.kr "상업적 이용 불가" 문구와 data.go.kr 공공누리 1유형 표기 중 무엇이 우선하는지 (상업화를 정하기 전에 서울시에 문의)
- TestFlight나 내부 테스트 트랙으로 활용사례 심사를 받을 수 있는지
- 코레일과 공항철도가 토요일에 휴일 시간표를 쓰는지
- 2호선 본선 열차번호 규칙(교차 검증 전), 신분당선과 GTX-A 열차번호 대응
- OSM 선로에 공공 역 좌표를 투영한 데이터가 ODbL 파생 데이터에 해당하는지. ODbL 의무를 지키기로 했으므로 막히는 문제는 아니고, 어떤 데이터까지 공개 대상인지 범위만 확인
- 마을버스가 위치 API에 포함되는지

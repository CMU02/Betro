# Betro 4단계 실시간 수집기 설계 (dev 모드, Cloudflare)

- 작성일: 2026-11-04
- 상태: 초안 (사용자 검토 전)
- 상위 문서: [`2026-10-30-data-collection-design.md`](2026-10-30-data-collection-design.md) (이하 "수집 설계"). 이 문서는 그 13장 4단계를 구체화합니다.
- 근거 자료: [`docs/research/2026-10-30-data-sources.md`](../../research/2026-10-30-data-sources.md) 9절(2026-11-03 정식 키 재측정)

**[사용자 결정]**은 사용자가 직접 정한 것이고, **[설계 판단]**은 설계자가 정한 것입니다. 설계 판단은 구현 중에 근거가 생기면 바꿔도 됩니다. 이 문서와 수집 설계가 다르면 이 문서를 따릅니다(8절에 바뀐 항목을 모았습니다).

---

## 1. 목적

1~3단계로 정적 참조 데이터(역 대응표, 선로, 시간표, 버스 노선·구간)가 준비됐습니다. 4단계는 **실시간 상태를 끊김 없이 모아 정규화하고, 원본과 관측을 이력으로 남기는 수집기**를 만듭니다. 공공 API 한도 승인은 앱 출시 뒤에야 받을 수 있으므로(수집 설계 13장), 4단계는 승인 전 한도(`dev` 모드)에서 돌아가야 하고, 승인 후(`prod` 모드)에는 설정만 바꿔 전체 규모로 넘어갈 수 있어야 합니다.

이번 단계에서 호스팅을 Cloudflare로 정했습니다. 그래서 4단계에는 **기존 API 서버를 Cloudflare Workers로 옮기는 작업**도 함께 들어갑니다. 서버 코드가 작아서(`apps/server`, `packages/api`, `packages/auth` 합계 287줄) 먼저 옮기고, 그 위에 수집기를 올립니다.

## 2. 목표, 범위 밖, 실패 기준

### 목표

1. API 서버를 Cloudflare Workers + Hono로 옮기고, DB를 D1으로 바꾼다. 기존 기능(oRPC 라우터, better-auth)은 그대로 동작한다.
2. 이 Mac에서 1~3단계 참조 데이터를 다시 적재하고, 현재 배치를 D1으로 올리는 명령을 만든다.
3. Durable Object 하나로 수집기를 만든다. `dev` 모드에서 지하철 전 노선과 버스 시험 노선 2개를 하루 한도 안에서 모은다.
4. 수집 설계 8장의 관측 이벤트로 정규화하고, 원본과 관측을 R2에 이력으로 남긴다.
5. 수집 상태를 상태 페이지에서 보고, 수집이 멈추면 휴대폰으로 알림을 받는다.
6. 하루 동안 끊김 없이 수집하고, 일일 보고서로 그 사실을 확인한다(4단계 완료 기준).

### 범위 밖

- **보간 엔진**(서버 쪽 상태 추정, 앱 쪽 움직임 계산): 다음 설계 문서입니다. 4단계는 수집 설계 10장의 계약(최신 상태, 관측 이벤트)을 제공하는 데까지입니다.
- **앱이 실시간 데이터를 받아 그리는 작업**: 4단계에서는 스냅샷 엔드포인트만 만들고 앱은 아직 붙이지 않습니다.
- **앱용 참조 데이터 묶음**(수집 설계 9.4절)과 **파생 통계**(9.3절, 6단계).
- **스냅샷 CDN 구성**(`betro-cdn.cmu02-studio.com`, R2 공개 버킷, 캐시 규칙): 앱이 스냅샷을 실제로 쓰기 시작할 때 정합니다.
- **도메인 등록 기관 이전**(가비아 → Cloudflare Registrar, 만기 2026-11-29): 사용자가 따로 진행합니다. DNS는 이미 Cloudflare에 있어서 4단계 작업은 이전 여부와 상관없이 진행됩니다. 기존 레코드(루트, `www`, `cleanbreath`의 Vercel 연결, Google 사이트 확인 TXT)는 건드리지 않습니다.
- **마을버스**: 위치 API에는 나오지만(재측정 9절) 3단계 정적 데이터 범위에서 뺐으므로 이번에도 넣지 않습니다.
- **`prod` 모드 운영**: 코드 경로와 설정은 만들지만, 실제 전체 규모 운영은 한도 승인 후(5~6단계)입니다.
- `apps/web`은 계속 Vercel에 둡니다. 이번 작업에서 건드리지 않고, 서버 이전 뒤 웹의 로그인·대시보드가 동작하지 않아도 됩니다(사용자 결정).

### 실패로 보는 것

- 수집이 멈췄는데 알림이 오지 않는다.
- 하루 호출 수가 한도를 넘어 키가 막힌다. 배포·재시작 중에 수집기가 둘 떠서 호출 수를 따로 세는 경우도 포함합니다.
- 공공 API 키가 로그, 이력 파일, 상태 페이지, 응답 본문에 남는다.
- 관측을 버린다. 품질 문제는 버리지 않고 플래그로 남겨야 합니다(수집 설계 10장 5).
- 기존 EC2(CleanBreath, PickTrip)를 건드린다.

### 3.1 Cloudflare로 정한 근거 (2026-11-04 측정)

측정용 Worker와 Durable Object를 배포해 두 API를 직접 불러 봤습니다(측정 후 삭제).

| 실행 위치 | 실제 지역 | 지하철 위치 | 지하철 ALL (1.8MB) | 버스 위치 |
|---|---|---|---|---|
| Worker | SEA (시애틀) | 200, 547ms | 200, 2,960행 전량, 1.6초 | 200, 1.1초 |
| Durable Object (위치 지정 없음) | SJC (산호세) | 200, 525ms | 200, 2,980행 전량, 2.4초 | 200, 772ms |
| Durable Object (`apac`) | KIX (오사카, 일본 IP) | 200, 315ms | 200, 2,980행 전량, 0.6초 | 200, 179ms |

두 API 모두 Cloudflare의 미국·일본 IP에서 정상 응답했습니다. 수집기는 `apac`으로 만들 때 가장 빠릅니다.

## 4. 수집기

### 4.1 구조

```
Cloudflare
├─ Worker "betro-server" (Hono)          betro.cmu02-studio.com
│   ├─ /rpc/*, /api/*            기존 oRPC 라우터 + better-auth
│   └─ /v1/snapshot/{subway,bus}  최신 스냅샷 (수집기에서 읽음)
├─ 상태 페이지 (Cloudflare Access로 보호)  betro-status.cmu02-studio.com
│   └─ /, /status.json
├─ Durable Object "Collector" (이름 하나 = 인스턴스 하나, apac)
│   ├─ alarm으로 주기마다 깨어나 상류 폴링 → 정규화 → 최신 상태 갱신
│   ├─ DO SQLite: 하루 호출 수, 소스별 직전 응답 해시, 차량별 마지막 관측, 5분 지표 7일 치
│   └─ R2로 이력 파일과 일일 보고서를 씀
├─ D1 "betro"      참조 데이터(현재 배치), 인증 테이블
└─ R2 "betro-data" raw/, events/, reports/
```

- 수집기는 Durable Object 이름 하나(예: `collector-v1`)로만 만듭니다. Durable Object는 이름 하나에 인스턴스 하나가 보장되므로, 수집 설계 5장의 "리더 잠금"은 Durable Object가 대신합니다. **[설계 판단]**
- 호출 수, 직전 상태처럼 재시작 뒤에도 이어져야 하는 값은 메모리가 아니라 DO SQLite에 둡니다. 메모리의 최신 상태는 DO가 다시 깨어날 때 SQLite에서 복원합니다.
- 메모리는 isolate당 128MB입니다. 참조 데이터는 전부 올리지 않고, 정규화에 필요한 것만 노선별로 읽습니다(4.5).

### 4.2 모드와 호출 계획

모드는 설정 하나(`COLLECTOR_MODE=dev|prod`)로 바꿉니다. 운행 시간(KST 05:00~01:00, 20시간)에만 폴링합니다. 운행 시간 밖에는 다음 05:00까지 alarm을 미룹니다. **[설계 판단]** 운행 시간 경계는 설정으로 둡니다.

| | `dev` | `prod` |
|---|---|---|
| 지하철 | ALL 1회. 약 80초마다, 하루 약 900건 | 19개 노선 `realtimePosition/0/999/<노선명>`. 20초마다 |
| 버스 | 6411, 150을 번갈아. 노선마다 약 2.7분 간격, 하루 약 900건 | 3단계 현재 배치의 전 노선. 목표 주기 30초, 운행 종료 노선은 쉼 |
| 하루 예산 | 소스별 1,000건 중 900건. 나머지는 재시도 여유 | 승인된 한도의 90% |

- **지하철 소스를 모드마다 다르게 둔 이유**: ALL은 1회로 전 노선을 주지만, 2호선에서 같은 상태 전이가 위치 API보다 20~30초(한 주기) 늦게 나왔고 상태 전이도 덜 보였습니다(재측정 9절). 하루 1,000건 안에서는 ALL만 전 노선을 볼 수 있으므로 `dev`는 ALL, 승인 후 `prod`는 위치 API입니다.
- **주기**: 원천이 약 20초 단위로 바뀌므로(지하철 중앙값 20초, 버스 `dataTm` 중앙값 18초) `prod`에서도 20초보다 자주 부르지 않습니다.
- **예산**: 소스별로 하루 호출 수를 세고 KST 0시에 초기화합니다. 재시도도 1건으로 셉니다. 남은 예산이 0이면 그 소스는 그날 더 부르지 않습니다. 예산이 모자라면 남은 운행 시간에 맞춰 주기를 늘립니다(수집 설계 7.2). 지하철 API는 한도 초과를 알리는 오류 코드가 없으므로 자체 카운터가 유일한 안전장치입니다.
- **호출 간격 제어**: `prod` 버스는 초당 10건 이하(토큰 버킷, 설정 가능)로 부릅니다(수집 설계 7.2).
- **키를 같이 쓰는 호출 [설계 판단]**: 자체 카운터는 수집기 자신의 호출만 셉니다.
  - 지하철 하루 1,000건은 **실시간 지하철 API에만, 인증키 1개당** 걸립니다. 역사마스터·역 검색 같은 일반 API는 횟수 제한이 없습니다(조사 보고서, 2026-10-31 확인). 지금 키(`SEOUL_OPEN_API_KEY`)는 일반 API와 `swopenAPI`에서 모두 동작했습니다. 그래서 이 Mac의 1~2단계 재적재는 실시간 한도를 쓰지 않습니다.
  - 버스 1,000건은 오퍼레이션별입니다. 3단계가 쓴 노선정보 오퍼레이션(`getStaionByRoute`, `getRoutePath`)과 수집기가 쓰는 `getBusPosByRtid`는 한도가 따로입니다.
  - 그래도 로컬 `wrangler dev`, 측정 스크립트처럼 같은 실시간 오퍼레이션을 부르는 곳은 한도를 같이 씁니다. 그래서 로컬 개발과 테스트는 기본값으로 저장된 표본 응답을 쓰고, 실제 상류 호출은 명시적인 설정을 켰을 때만 합니다. 하루 시험 운행 중에는 수집기 밖에서 실시간 오퍼레이션을 부르지 않습니다.

### 4.3 상류 호출

- 두 API 모두 HTTP만 됩니다(HTTPS는 시간초과). gzip을 지원하지 않습니다.
- 요청마다 타임아웃 10초, 실패하면 지수 백오프로 재시도합니다. 한 노선의 실패가 다른 노선을 막지 않습니다.
- 오류 분류와 처리는 수집 설계 7.5절 표를 그대로 따릅니다. HTTP 401(키 문제)이면 그 소스를 멈추고 즉시 알림을 보냅니다(5.3).
- 키는 Worker secret(`SEOUL_OPEN_API_KEY`, `DATA_GO_KR_API_KEY`)으로만 둡니다. 지하철 키는 URL 경로에, 버스 키는 쿼리에 들어가므로, 요청 URL을 로그·이력·오류 메시지에 남길 때는 키를 지운 형태로만 남깁니다.

### 4.4 변화 감지

- 소스별로 응답 본문 해시를 직전과 비교합니다. 같으면 원본은 해시만 남기고(4.6), 관측 이벤트를 만들지 않습니다.
- 지하철: 같은 열차의 (역, 상태)가 직전과 같으면 이벤트를 만들지 않습니다. 상태가 바뀐 경우만 "상태 전이 이벤트"를 만듭니다.
- 버스: 차량별로 `dataTm`이 직전과 같으면 관측을 만들지 않습니다.

### 4.5 정규화

출력은 수집 설계 8장의 `SubwayObservation`, `BusObservation`을 그대로 따릅니다. 시각은 UTC epoch ms이고 원본 KST 문자열도 보존합니다.

**지하철**
- `statnId`로 역 대응표(1단계)를 찾고, 선로 위 역 거리(`track_station`)로 위치를 구합니다.
- 열차번호를 시간표 `trip`에 잇습니다(수집 설계 6.4). 매칭에 필요한 건 trip 단위 정보(노선, 요일, 방향, 열차번호, 출발·도착역)뿐이라 trip 약 2만 건만 메모리에 둡니다. 정차 시각(`stop_time`, 약 56만 행)은 메모리에 올리지 않습니다. **[설계 판단]**
- 재측정에서 나온 원천 결함을 반영합니다.
  - **7호선은 위치 API와 ALL의 열차번호가 다릅니다**(35대 중 14대). 두 소스를 열차번호로 서로 조인하지 않습니다. 어느 쪽 번호가 시간표와 맞는지는 아직 모르므로, 노선별 매칭률(5.1)로 확인합니다.
  - **신분당선 ALL 행의 `recptnDt`는 미래 시각**입니다(최대 5분). 받은 시각보다 미래인 `recptnDt`는 관측 시각으로 쓰지 않고 플래그를 답니다.
  - 코레일 계열 노선(1호선, 경의중앙, 경춘, 공항철도 등)은 3분 넘게 묵은 행이 많습니다. 버리지 않고 신선도를 계산해 플래그로 남깁니다.
- ALL은 `updnLine`이 "상행/하행"(2호선은 "내선/외선"), 위치 API는 "0/1"입니다. 내부 방향 값으로 통일합니다.
- **ALL 행에서 열차 하나의 (역, 상태)를 뽑는 규칙 [설계 판단]**: ALL은 역별 도착 목록이라 한 열차가 여러 역의 행에 동시에 나옵니다(예: 한 역에서 `arvlCd` 0, 다음 역에서 3·4·5, 그다음 역에서 99). 수집 설계 8장의 관측은 열차당 역 하나, 상태 하나이므로 다음처럼 줄입니다.
  1. (`subwayId`, `btrainNo`)로 행을 묶습니다.
  2. 그 행의 역 기준 상태로 바꿉니다. `arvlCd` 0·1·2는 그 역(`statnId`)의 진입·도착·출발입니다. 3(전역출발)은 그 역의 전역출발입니다(위치 API `trainSttus` 3과 같은 뜻). 4·5(전역진입·전역도착)는 이전 역(`statnFid`)의 진입·도착으로 바꿉니다. 99(운행중)는 위치를 정하지 않습니다.
  3. 한 열차에 0~5에서 나온 후보가 여럿이면 진행 방향으로 가장 앞선 것(선로 위 거리 기준) 하나를 대표로 씁니다. 후보끼리 서로 다른 역을 가리키며 모순되면 대표는 고르되 플래그를 답니다.
  4. 99만 있는 열차와 ALL에만 나오는 번호(출고 전·서울 밖 열차로 보이는 것, 재측정에서 같은 시점 468개 대 420대)는 관측으로 남기되 `position_unknown` 같은 플래그를 달고, 상태 페이지의 노선별 열차 수에는 넣지 않습니다.
  - 재측정 때 쓴 비교 스크립트의 규칙(`arvlCd` 0·1·2만 사용)은 측정용이었고, 이 규칙이 그것을 대신합니다. 원본을 남기므로 규칙을 바꾸면 다시 계산할 수 있습니다.

**버스**
- `getBusPosByRtid`의 `sectDist`와 `fullSectDist`는 km입니다. m로 바꿔 3단계 구간(`bus_route_segment`, `fromSeq = sectOrd`)에 얹습니다: `startM + (sectDist / fullSectDist) × (endM − startM)`. 재측정에서 `fullSectDist×1000`이 3단계 원본 구간 거리와 19/19 일치했습니다.
- `gpsX/gpsY`를 노선 모양에 투영한 거리도 따로 구하고, 두 값이 크게 다르면 플래그를 답니다. `prod`에서 전 노선의 모양을 메모리에 다 올리기 어려우면 투영은 노선별로 필요할 때 읽습니다. **[설계 판단]**
- 같은 차량의 위치가 직전보다 뒤로 가면 "역행" 플래그를 답니다. `dataTm`이 1~2초 뒤로 가는 경우도 관측됐으므로 시각 역행도 플래그로 남깁니다.

### 4.6 이력 (R2)

- **원본**: `raw/<source>/<YYYY>/<MM>/<DD>/<HH>.ndjson.gz` (KST 기준 시각). 한 줄에 출처, 키를 지운 요청 정보, 받은 시각, HTTP 상태, 본문 해시, 본문을 둡니다. 본문이 직전과 같으면 본문 대신 해시만 둡니다.
- **관측 이벤트**: `events/<subway|bus>/<YYYY>/<MM>/<DD>/<HH>.ndjson.gz`.
- 압축은 gzip입니다(Workers의 `CompressionStream`). 수집 설계 9.1의 zstd와 일 단위 파일에서 바꿨습니다. Workers에서 zstd를 쓸 수 없고, 메모리 128MB 안에서 버퍼를 작게 두려는 **[설계 판단]**입니다.
- 버퍼가 일정 크기를 넘거나 시간이 바뀌면 R2에 씁니다. 한 시간 파일을 여러 조각으로 나눠 써도 됩니다(조각 번호를 파일 이름에 붙임). 쓰기 전에 DO가 내려가도 잃는 양이 몇 분 이내가 되게 합니다.
- 보관 기간: 원본 30일, 관측 이벤트 1년(수집 설계 9.1). R2 수명 주기 규칙(접두사별 삭제)으로 지웁니다.
- `dev` 모드 용량 추정: 지하철 ALL이 하루 약 900회 × 1.8MB인데, 약 절반은 직전과 같아 해시만 남습니다. gzip 뒤 하루 수백 MB입니다. R2 무료 10GB는 원본 30일 보관이면 대체로 안에 들어갈 것으로 봅니다(측정 후 조정).

### 4.7 최신 상태와 스냅샷

- 수집기는 노선별·차량별 마지막 관측을 최신 상태로 들고 있습니다(수집 설계 8장). 보간 엔진(다음 단계)은 이것을 읽습니다.
- Worker의 `GET /v1/snapshot/subway`, `GET /v1/snapshot/bus`는 수집기에서 최신 상태를 받아 JSON으로 돌려줍니다. `Cache-Control: public, max-age=10`과 `ETag`를 붙이고, `If-None-Match`가 같으면 304를 돌려줍니다.
- 4단계에서는 앱이 아직 이 엔드포인트를 쓰지 않습니다. 스냅샷 형식은 보간 엔진 설계에서 다시 정할 수 있으므로 `v1`으로 둡니다. **[설계 판단]**

### 5.2 기록

- 5분 지표는 DO SQLite에 7일 치를 둡니다. 상태 페이지 그래프가 여기서 읽습니다.
- 매일 KST 0시에 예산을 초기화하면서 그날 요약을 `reports/<YYYY-MM-DD>.json`으로 R2에 씁니다. 운행 시간 중 "멈춤"이었던 구간, 소스별 호출 수, 오류 수, 노선별 평균 차량 수와 매칭률을 담습니다. 4단계 완료 판정은 이 파일로 합니다.
- 오류 원문은 Workers Logs에 남깁니다. 키는 남기지 않습니다.

### 5.3 알림

- 수집 상태가 "멈춤"이 되거나 HTTP 401이 나면 푸시를 보냅니다. 같은 종류의 알림은 30분에 한 번만 보냅니다. 회복하면 회복 알림을 한 번 보냅니다.
- 이미 동작하는 FCM으로 Betro 앱에 보냅니다(Firebase 프로젝트 `betro-a77a2`). Worker가 FCM HTTP v1 API를 부르려면 Firebase 서비스 계정 키를 Worker secret으로 넣어야 합니다. 받을 기기 토큰은 4단계에서는 개발자 기기 토큰 하나를 secret으로 넣습니다. **[설계 판단]**
- FCM 연동이 막히면 Discord 웹훅 하나로 바꿔도 됩니다.

## 6. API 서버 이전

- `apps/server`를 Hono 기반 Worker로 바꿉니다. oRPC는 fetch 핸들러로, better-auth는 Hono 라우트로 붙입니다. CORS 설정은 기존 값을 그대로 옮깁니다.
- `packages/db`의 `createDb`는 D1 바인딩을 받도록 바꿉니다. Drizzle의 D1 드라이버를 씁니다. 마이그레이션은 기존 `packages/db/src/migrations`를 D1에 적용합니다. 로컬 개발은 `wrangler dev`의 로컬 D1을 씁니다.
- 환경 변수와 secret: `apps/server/.env.schema`는 Vercel 변수로 URL을 만들고 있습니다. Worker 설정(`wrangler` 설정의 vars와 secret)으로 옮깁니다. `BETTER_AUTH_URL`은 `https://betro.cmu02-studio.com`입니다. 웹(`apps/web`)은 이번에 맞추지 않으므로 `CORS_ORIGIN`·`trustedOrigins`는 앱과 로컬 개발에 필요한 값만 둡니다.
- Worker는 Workers 커스텀 도메인으로 `betro.cmu02-studio.com`에 붙입니다. DNS 레코드와 인증서는 Cloudflare가 만들어 줍니다. `workers.dev` 주소는 끕니다(같은 API가 두 주소로 열리지 않게). **[설계 판단]**
- 실제 사용자 계정이 없으므로 데이터 이전 단계는 없습니다. D1에는 마이그레이션만 적용합니다.
- `packages/infra/alchemy.run.ts`(Prisma Compute 배포)는 wrangler 설정으로 대체합니다. 지울지 남길지는 구현하는 사람이 정합니다.
- 앱(`apps/native`)의 `EXPO_PUBLIC_SERVER_URL`을 `https://betro.cmu02-studio.com`으로 바꿔, 기존 앱 기능(로그인, 푸시)이 그대로 되는지 확인합니다.

## 7. 참조 데이터

- 이 Mac에서 1~2단계를 다시 적재합니다. 원본은 `data/raw/`에 이미 있고, 키는 `SEOUL_OPEN_API_KEY`만 필요합니다. 원본이 그사이 바뀌었으면 Windows PC 결과와 다를 수 있으므로 각 단계의 검증 보고서로 확인합니다.
- `transit-static`은 지금처럼 이 Mac에서 libsql `local.db`로 빌드합니다. 그 뒤 **현재 배치만 D1으로 올리는 명령**(`bun transit publish:d1` 등)을 새로 둡니다.
  - 배치 ID와 manifest를 그대로 들고 갑니다. D1에도 이전 배치를 남겨, 문제가 생기면 이전 배치를 현재로 되돌릴 수 있게 합니다.
  - D1은 쿼리 하나에 바인딩 100개까지만 받으므로 나눠서 넣습니다.
  - 같은 manifest가 이미 D1에 있으면 다시 올리지 않습니다.
- 수집기는 시작할 때와 D1의 현재 배치가 바뀌었을 때 필요한 참조 데이터를 다시 읽습니다. 수집 도중 배치가 바뀌어도 한 주기 안에서는 같은 배치를 씁니다.

## 8. 수집 설계에서 바뀐 항목

| 수집 설계 | 바뀐 내용 |
|---|---|
| 3장 서버 스택 "기존 `apps/server` (Bun + Fastify)에 수집기를 둠" | API는 Workers + Hono, 수집기는 Durable Object |
| 5장 리더 잠금(DB lease) | Durable Object의 단일 인스턴스 보장으로 대체 |
| 5장 호스팅 지역 확인 | 확인 완료(3.1). 수집기는 `apac`(오사카) |
| 7.1 지하철 주 소스 결정 | `dev`는 ALL, `prod`는 위치 API |
| 9.1 일 단위 NDJSON + zstd | 시간 단위 NDJSON + gzip |
| 9.2 참조 DB `dialect: "turso"` libsql | 빌드는 이 Mac의 libsql, 서비스는 D1 |
| 14장 구현자가 정할 것(호스팅, 저장, 지표 도구, 배치 실행) | 이 문서에서 정함 |

## 9. 완료 기준

1. 새 Worker에서 기존 앱의 로그인과 푸시가 동작한다.
2. 1~3단계 현재 배치가 D1에 올라가 있고, 수집기가 그것으로 정규화한다.
3. `dev` 모드로 운행 시간 하루(05:00~01:00)를 돌린 일일 보고서에서, 소스별로 "멈춤" 구간이 없고 하루 호출 수가 한도를 넘지 않았다.
4. 상태 페이지에서 11장 지표(5.1의 범위)를 볼 수 있고, 수집을 일부러 멈췄을 때 알림이 온다.
5. 원본과 관측 이벤트가 R2에 시간 단위로 쌓이고, 키가 어디에도 남지 않는다.

## 11. 위험과 확인 못 한 것

- **한국 사용자 요청이 해외 지점으로 갈 수 있습니다.** 국내 회선에서 보낸 요청이 시애틀 지점에서 처리됐습니다(3.1, 한 회선 한 번 측정). 스냅샷 폴링은 20초 간격이라 영향이 작지만, 일반 API 호출은 느려질 수 있습니다.
- **Durable Object 위치는 보장되지 않습니다.** `apac`은 지역 힌트일 뿐입니다. 다른 곳에 만들어져도 두 API는 응답했지만(3.1) 지연이 커집니다.
- **Cloudflare에서 상류 API가 막히면** 수집기만 기존 EC2에 컨테이너로 옮깁니다(사용자 결정). 이때도 R2와 D1은 그대로 씁니다.
- 7호선에서 시간표와 맞는 열차번호가 위치 API 쪽인지 ALL 쪽인지 모릅니다.
- 평일 08시 첨두 동시운행 수, 하루 한도 초과 시 응답 형식은 아직 재지 않았습니다(재측정 9절).
- 승인 후 `prod` 모드의 Workers 비용은 추정만 했습니다(CPU 초과분 월 1달러 미만).
